2. AVENUE A — Databases
--------------------------------------------------------------------------------
A1. sqlite-vec for note_search (DONE 2026-08-17 — completed.md #124)
    - What: load `sqlite-vec` extension in research.db; add a
      vec0 virtual table keyed on file_path with FLOAT[blob] vectors; replace
      the Python per-row cosine loop in /api/search hybrid ranking with a
      single KNN SELECT + the existing BM25 half.
    - Why here: embeddings ALREADY exist as JSON in the same DB; the swap is
      local to rebuild_note_search + app.py search; sqlite-vec supports
      metadata columns + filtering (Nov 2024 release) and KNN-as-SQL with
      distance constraints (verified, §9). Python>=3.14 wheels exist via pip
      `sqlite-vec`.
    - Risks: extension-load policy (we already ship sqlite-spellfix the same
      way); planner limits on JOIN+WHERE KNN filters (issue #196) — our
      filter set (sector) is one WHERE, fine.
    - Sizing: ~1 day + tests (suite pattern: test_rebuild_note_search,
      test_api_search already pin hybrid behavior).

A2. DuckDB vss HNSW on v_embeddings (= existing deferred N5-5; UNCHANGED)
    - The extension is officially experimental and HNSW indexes are
      in-memory-only unless an experimental persistence flag is set (§9).
      Brute force at 1k vectors is ~3 ms — already tracked in pending.md;
      keep the quarterly re-eval cadence. Do not build on experimental
      persistence for a git-snapshotted DB.

A3. Parquet-first analytics ("lakehouse mode") (OPTIONAL, medium)
    - snapshots/parquet is already the transport of record. DuckDB can query
      the parquet tree directly; a `make analytics` entry point running
      read-only SQL over snapshots/ would give git-diffable, DB-less
      analytics (year-over-year edge growth, sector churn) without touching
      live DBs. Cheap because Option B did the hard part.
    - Not a replacement for research.db (FTS5 + spellfix have no parquet
      equivalent).

A4. SQLite core richness (MICRO-WINS)
    - Generated columns for normalized_name/ticker-upper; JSONB functions for
      embedding JSON during an A1 migration; `PRAGMA optimize` on close.
    - Only worth bundling with A1's migration, not standalone.

ANTI-RECOMMENDATIONS (deliberate no's)
    - LanceDB / Chroma / FAISS: a THIRD store for 1,046 vectors adds sync
      surface for zero recall gain at this scale.
    - Turso/libSQL: single-user local repo; networked SQLite buys nothing.
    - Kùzu: see C4 — upstream archived Oct 2025.
    - Postgres/pgvector: contradicts the embedded, git-shippable design.

3. AVENUE B — YAML richness (pipeline-native; Obsidian explicitly out of scope)
--------------------------------------------------------------------------------
    [User decision 2026-08-17: Obsidian is not an active use case outside of
    the YAML itself. Nothing in this avenue may depend on Obsidian plugins,
    .base files, Dataview, or vault-UI behaviour.]

B1. Typed frontmatter contract (JSON Schema) (RECOMMENDED, small)
    - Formalize the de-facto keys (per note type: company/theme/sector/…)
      into doc/schema/frontmatter.company.v1.json etc.; validate in
      static_checks via `jsonschema` (new dev-only dep); generate the key
      list in doc/ from the schema so humans and validators share one
      source. Catches drift the custom checks miss (wrong types like
      market_cap: "null" string, rogue keys).
    - Keeps YAML human-first: schema is a validator, not a generator.
      Purely for OUR pipeline (static_checks, verify_notes,
      extract_relations, app.parse_yaml_frontmatter).

B2. Relation sidecars with provenance (MEDIUM, builds on H4 cleanup)
    - Promote structured edges to per-relation YAML sidecars (e.g.
      _relations/JSW_Paints.yaml) carrying edge_type, counterparties,
      as_of, confidence, source permalink — the _pending_relations.txt
      queue already proved the review workflow; sidecars make accepted
      edges auditable and re-ingestible (extract_relations already speaks
      YAML).
    - Review surface = our own tools (CLI report + tests), not any vault UI.

B3. ANTI-RECOMMENDATION: YAML anchors/merge keys in frontmatter.
    - Maintenance scripts (static_checks, verify_notes, extract_relations)
      parse flat YAML with grep-able structure; anchors break the flat-file
      grep-ability they rely on and complicate PyYAML round-trips.
    - Keep frontmatter flat; share structure via the B1 schema instead.
4. AVENUE C — Graph
--------------------------------------------------------------------------------
C1. GraphRAG-lite "context packs" (RECOMMENDED, small-medium, high leverage)
    - We already have every ingredient: /api/graph/semantic/<name> (kNN seed
      + hop expansion), peers/neighbors/shortest routes, frontmatter
      context. Package a `context_pack(entity, hops, budget)` helper that
      serializes a scored subgraph to markdown (entities, edges with types/
      years, sector rollup) — the exact artifact an LLM (or the D5 agent
      workflow) consumes. No new deps; pure composition.
    - This is the highest value-per-line item in the graph avenue.

C2. Link-prediction as a suggestion workflow (MEDIUM)
    - onager_link_prediction exists and is tested. Productize: nightly
      top-N predicted edges NOT already present -> appended to
      _pending_relations.txt with confidence -> human accepts via
      existing review flow -> parse_newsletter ingestion unchanged.
      Closed-loop "suggested relations" with zero new UI.

C3. Temporal graph analytics (MEDIUM, optional)
    - edges-by-year route + as_of normalization already exist (tests pin
      _normalise_as_of). Add time-sliced metrics (per-year degree,
      community drift via louvain per year) feeding A3's analytics views.

C4. Kùzu / property-graph engine (BLOCKED — do not adopt now)
    - Kùzu was ARCHIVED 2025-10-10 after Apple acquired the company;
      maintenance passes to community forks (Bighorn by Kineviz et al.)
      which are weeks old (§9). We also just retired duckpgq in favor of
      recursive CTEs (D-decision 2026-08-14) and Onager. Revisit only if
      (a) a fork stabilizes with releases, AND (b) Cypher path queries
      measurably beat the CTE layer on our 12-table star.

C5. Visualization (DEFER)
    - Cytoscape canvas is comfortable at 1,209 entities. WebGL (Cosmograph/
    sigma.js) only if entity count grows 10x.
